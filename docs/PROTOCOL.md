# Протокол файлового канала «телефон ⇄ Яндекс.Диск ⇄ сервер»

Каноническая спецификация. Каноничность: серверный адаптер (`yd-adapter`) и клиент
(`echo-pult`) обязаны ей следовать; при расхождении кода с этим документом правится код.

## 1. Общая схема

Яндекс.Диск — тупой транспорт: три папки в корне личного Диска. Логики задач на Диске нет.

```
телефон (Android, Flutter)
    │  PUT  in/<ts>-<hash>.json  +  in/att/<id>/<файл>
    │  GET  список out/, скачивание ответов
    ▼
Яндекс.Диск   /echo/{in,out,archive}/…
    ▲
    │  REST API v1 (токен из .env / secure storage)
    ▼
сервер: yd-adapter  ──▶  /opt/echo-bot/queue  ──(ssh)──▶  воркеры Hermes
```

## 2. Раскладка

```
/echo/                              корень канала
  in/<ts>-<hash>.json               сообщение от телефона
  in/att/<msgid>/<файл>             вложения сообщения
  out/<ts>-<hash>.json              ответ сервера
  out/att/<msgid>/<файл>            вложения ответа
  archive/in/<имя>                  обработано (перекладывает адаптер)
  archive/out/<имя>                 прочитано/устарело
  archive/broken/<имя>              нечитаемый JSON
```

Формат имени: `<ts>-<hash>.json`, где `<ts>` — UTC-время создания `20260918T150233Z`,
`<hash>` — 4 hex-символа случайности. Имя сортируется лексикографически = хронологически,
порядок восстанавливается без разбора JSON. `<msgid>` = имя файла-конверта без `.json`.

## 3. Кто что пишет

| Участник | Пишет | Читает | Удаляет/перемещает |
|---|---|---|---|
| телефон | `in/*.json`, `in/att/<msgid>/*` | `out/`, `archive/in/` (квитанции) | ничего |
| адаптер | `out/*.json`, `out/att/<msgid>/*`, `archive/**` | `in/`, `out/` | `in/`, `out/`, `archive/` |
| воркеры | — (только локальная очередь через ssh) | — | ничего |

## 4. Конверт задачи (`in/<ts>-<hash>.json`)

```json
{
  "id": "20260918T150233Z-a1b2",
  "ts": 1789743753,
  "kind": "agent",
  "text": "чекни новые сообщения в bitrix24",
  "worker": "any",
  "context": [{"role": "user", "content": "…"}, {"role": "assistant", "content": "…"}],
  "attachments": [{"path": "in/att/20260918T150233Z-a1b2/photo.jpg", "name": "photo.jpg", "mime": "image/jpeg"}]
}
```

- `id` — равен имени файла без `.json`; глобально уникален (timestamp + salt), не переиспользуется.
- `kind`:
  - `agent` — задача воркеру: адаптер кладёт её в локальную очередь `/opt/echo-bot/queue`;
  - `chat` — простой запрос к LLM: адаптер отвечает сам через OpenAI-совместимый
    `/chat/completions` (system-промпт сервера + `context` конверта + `text`), мимо очереди.
    **Вложения в `chat` не поддерживаются** — при их наличии адаптер вернёт `ok=false`.
- `worker` — `any | pc | laptop` (маршрутизация в очереди).
- `context` — последние ≤3 реплик клиентской ленты; сервер историю не хранит, лента — на клиенте.

## 5. Конверт ответа (`out/<ts>-<hash>.json`)

```json
{
  "id": "20260918T150401Z-c3d4",
  "ref": "20260918T150233Z-a1b2",
  "ts": 1789743841,
  "ok": true,
  "worker": "laptop",
  "text": "5 непрочитанных в 2 чатах задач …",
  "attachments": [{"path": "out/att/20260918T150401Z-c3d4/report.md", "name": "report.md", "mime": ""}]
}
```

- `ref` — `id` исходной задачи; по нему клиент связывает ответ с сообщением.
- `ok=false` — отказ (ошибка LLM, неподдерживаемые вложения и т.п.); `text` содержит
  человекочитаемую причину.

## 6. Правила протокола (вся защита от гонок)

1. **Файл-конверт никогда не переписывается.** Запись только новая, с новым именем.
   Правка опубликованного запрещена: у Диска побеждает последняя запись целиком, плюс
   появляются копии «файл (1).json».
2. **Вложения публикуются ДО конверта.** Появление конверта означает «всё сообщение на месте»:
   читатель, скачав конверт, вправе сразу тянуть вложения. Перед загрузкой вложения телефон
   обязан создать каталог `in/att/<msgid>/` по уровням: upload не создаёт родителей и отвечает
   `409 DiskPathDoesntExistsError` (проверено 21.09.2026). Адаптер заранее держит `in/att`
   и после успешной обработки сам удаляет `in/att/<msgid>/` (вложения уже скачаны в очередь)
3. **Публикация конверта — одним `PUT`** (`overwrite=false`). Полуфайлов в облаке не бывает.
   Ответ `409`/`423` на загрузку означает «имя занято»: сгенерировать новое имя, не перезаписывать.
   Нюанс (проверено 18.09.2026): индексация Диска асинхронна, поэтому `409` на дубликат может
   прийти с задержкой в секунды. Значит `409` — страховка, а не механизм защиты; основная
   защита — уникальность имён по построению (`<ts>-<hash>`).
   **Исключение — вложения результата** (`out/att/<id>/<имя>`): их путь детерминирован по
   `msgid` задачи, поэтому повторная публикация после обрыва идёт с `overwrite=true` —
   затирает прошлую попытку вместо `409`. Конверты так не публикуются никогда.
4. **Атомарность на сервере** — как в очереди: писать в `*.tmp`, затем `mv`.
5. **Удалять и перекладывать в `archive/` может только адаптер.** Клиент ничего не удаляет
   и не перемещает.
6. **`archive/` — квитанция.** Телефон, увидев свой `in/`-файл в `archive/in/`, рисует
   «доставлено». Адаптер, увидев свой `out/`-файл в `archive/out/`, знает, что чистить нечего.
7. **Идемпотентность адаптера** — локальный `state.json`: id обработанных конвертов; рестарт
   не выполняет задачу дважды.
8. **Очистка** — только адаптером, только в `archive/`, по возрасту имени (`RETENTION_DAYS`).
   `in/` и `out/` адаптер чистит только перекладыванием в `archive/`.

Правило «конверт публикуется последним» — критично: это единственный сигнал целостности
сообщения. Другого механизма (частичных загрузок, манифестов, блокировок) в Диске нет;
любой порядок «конверт раньше вложений» создаёт окно, когда читатель видит конверт без файлов.

## 7. Push-канал (ntfy, вне Диска)

Файловый канал остаётся единственным источником истины: телефон узнаёт об ответах опросом
`out/`. Поверх него работает best-effort push, чтобы ответ был виден за секунды, а не на
следующем опросе (15 с на открытом экране; в фоне телефон всё равно заморожен вендорским
«сберегателем» и опроса не ведёт).

```
адаптер ──POST https://ntfy.sh/<NTFY_TOPIC>──▶ ntfy.sh ──FCM──▶ приложение ntfy на телефоне
                                                                    │ тап по уведомлению
                                                                    ▼
                                              echopult://open?ref=<msgid> → echo-pult, ресинк
```

- Топик `NTFY_TOPIC` — случайная hex-строка, общий секрет адаптера и клиента (`lib/config.dart`).
  Кто знает топик — может читать уведомления и слать свои; поэтому содержимое ответа в push
  не передаётся: только заголовок, «Новый ответ» и deep link. Полный текст — только из
  конверта на Диске.
- Отправка — сразу после успешной публикации конверта в `out/` (все пути: chat-ответ,
  chat-отказ, результат воркера). Сбой push не влияет на цикл и не повторяется дольше
  одного ретрая: конверт уже опубликован.
- Доставка до телефона обеспечивается приложением ntfy (сборка Play, мгновенная доставка
  через FCM работает и в Doze). echo-pult сам фоновых соединений не держит.
- Deep link `echopult://open?ref=<msgid>` обрабатывается echo-pult (intent-filter в
  манифесте): приложение открывается и делает полный ресинк ленты. `ref` сейчас
  используется только как метка; лента сверяется по Диску.

## 8. Маппинг на локальную очередь (воркеры не меняются)

| Яндекс.Диск | Локальная очередь | Кто делает |
|---|---|---|
| `in/<ts>-<hash>.json` (kind=agent) | `inbox/<id>.json` (`id`, `worker`, `task`, `context`, `attachments`, `chat_id=0`) | адаптер |
| `in/att/<msgid>/<файл>` | `files/<id>/in/<файл>` | адаптер |
| `outbox/<id>.json` | `out/<ts>-<hash>.json` (`ref=id`) | адаптер |
| `files/<id>/out/<файл>` | `out/att/<msgid>/<файл>` | адаптер |
| `outbox/<id>.json` (опубликован) | → `done/<id>.json` | адаптер |
| `claimed/<id>.json.<worker>` старше `CLAIM_TIMEOUT` | → `inbox/` | адаптер |
| `in/<ts>-<hash>.json` (kind=chat) | LLM → сразу `out/<ts>-<hash>.json` | адаптер |

Схема задачи/результата очереди — как читает/пишет `scripts/agent_poller.py` воркера;
менять её запрещено.

## 9. Пример полного цикла

1. Телефон 15:02:33 UTC грузит вложение `in/att/20260918T150233Z-a1b2/photo.jpg`,
   затем конверт `in/20260918T150233Z-a1b2.json` (`kind: agent`, `text: "что в bitrix24?"`).
2. Адаптер (цикл 10 с): скачивает вложение в `queue/files/20260918T150233Z-a1b2/in/photo.jpg`,
   пишет `queue/inbox/20260918T150233Z-a1b2.json`, перекладывает конверт в
   `archive/in/20260918T150233Z-a1b2.json`, записывает id в `state.json`.
3. Воркер забирает задачу, отрабатывает, пишет `queue/outbox/20260918T150233Z-a1b2.json`.
4. Адаптер: грузит `out/att/20260918T150401Z-c3d4/report.md`, затем конверт
   `out/20260918T150401Z-c3d4.json` (`ref: 20260918T150233Z-a1b2`), уводит outbox-файл
   в `done/`. Телефон при следующем опросе видит ответ и (заглянув в `archive/in/`) —
   галочку «доставлено».
